# Buddygotchi

A macOS menu bar companion for AI coding agents (Claude Code, Cursor, Codex). Optionally drives an M5StickC Plus 2 over BLE. See [ARCHITECTURE.md](ARCHITECTURE.md) for the full design and [BUGS.md](BUGS.md) for known issues / doc-vs-impl drift.

## Architecture

Strict **inputs → core → outputs** separation:

- **Core** (`Core/`) is pure business logic — engine, reducer, state model, events. No UI imports, no I/O. The reducer takes timestamps from event `at` fields, never from a clock; tests inject `MockClock`.
- **Inputs** translate external events into `BuddyEvent`s and feed them to the engine. Two hook-delivery shapes are in use:
  - **Cursor** → `BuddygotchiSignal` Swift binary → `/hook/signal` (or `/hook/approve` in approval mode).
  - **Claude Code & Codex** → generated bash script `~/.buddygotchi/buddygotchi-hook.sh` (built into `HookInstaller.hookScriptContent`) → `/hook/event` or `/hook/approve`. The script reads `~/.buddygotchi/config.json` on every invocation, so toggling approval mode never requires a reinstall.
  - The `BuddygotchiHook` Swift target still ships in `Package.swift` but is **legacy/unused** — POSTs to a route that doesn't exist. Don't extend it.
- **Outputs** (`Views/`, `Outputs/`, `Notifications/`) implement `OutputProvider` and react to `stateDidChange`. The menu bar UI and ESP32 are bidirectional — both can call `engine.resolveApproval` to settle a pending `CheckedContinuation`. Derive everything from `BuddyState`, don't store parallel state.

When adding a new source, add an input adapter that emits `BuddyEvent`s. When adding a new display, implement `OutputProvider`. Neither should require changes to `Core/`.

## State & config

- `~/.buddygotchi/config.json` — `{ "port": 21321, "approvalMode": bool }`. Read on app start (`BuddyConfig.default`) and re-read by hook scripts on every invocation.
- `~/.buddygotchi/buddygotchi-hook.sh` — the bash hook script, regenerated by `HookInstaller` on install/reinstall.
- `~/.claude/settings.json`, `~/.cursor/hooks.json`, `~/.codex/hooks.json` (+ `[features] codex_hooks = true` in `~/.codex/config.toml`) — the per-agent hook registrations.

## Build & Run

```sh
cd app
swift build
swift run Buddygotchi
```

Tests (in-process):

```sh
swift test                                          # all (66 tests, ~1s)
swift test --filter ReducerTests                    # one suite
swift test --filter testDefaultSpeciesIsAKnownSpecies  # one test
```

Snapshot harness (renders real SwiftUI views to PNGs; disabled by default to keep CI headless-safe):

```sh
mkdir -p /tmp/buddy-snapshots && touch /tmp/buddy-snapshots/.enable
swift test --disable-sandbox --filter SnapshotHarnessTests
```

End-to-end HTTP smoke against a running daemon (the bash sandbox can't reach localhost — run in a real terminal):

```sh
(cd app && swift run Buddygotchi) &
app/tools/e2e-smoke.sh             # all three agents
app/tools/e2e/cursor.sh            # one agent
```

Quick health probe:

```sh
curl http://localhost:21321/healthz
```

Reset onboarding (so the first-run wizard reappears):

```sh
defaults delete Buddygotchi setupCompleted
```

## ESP32 dev tools

```sh
python3 src/outputs/esp32/tools/screenshot.py --out /tmp/buddy.png
python3 src/outputs/esp32/tools/button.py --mock a   # arm fake prompt + press A (approve)
python3 src/outputs/esp32/tools/button.py b          # press B (deny) against whatever's live
```

Screenshot reads the panel via `M5.Display.readRect`, so direct-to-LCD draws (landscape clock, GIF frames) are captured too — not just sprite content. Button injects a synthetic press through the firmware's real approval path; `--mock` arms a fake prompt so it works offline. Both `screenshot`/`btn`/`mockprompt` are non-JSON debug commands handled by `handleSerialCommand` in `firmware/main.cpp`.

## Key Files

| File | Role |
|------|------|
| `Core/BuddyEngine.swift` | Central orchestrator — all state flows through here; holds `pendingApprovals` and `processWatchers` |
| `Core/BuddyReducer.swift` | Pure reducer — the only place state transitions are defined |
| `Core/BuddyState.swift` | Single source of truth for all outputs |
| `Server/HookServer.swift` | HTTP input — translates hook payloads to engine events |
| `Install/HookInstaller.swift` | Per-agent hook registration; the bash hook script lives inline as `hookScriptContent` |
| `Outputs/ESP32/Heartbeat.swift` | Wire-format contract with the ESP32 firmware (`firmware/data.h::_applyJson`) |
| `Views/PopoverView.swift` | Main UI — live view, tool card, approve/deny buttons |
| `Buddies/BuddySprites.swift` | ASCII art data (5 species × 7 states × animation frames) |

## Watch out for

- **`Stop` (Claude Code) maps to `celebrate`, not `stop_working`** — see BUGS.md for the doc-vs-impl history. `TaskCompleted` and `SubagentStart` in `SignalCLI.signalMap["claude-code"]` are vestigial; Claude Code's hooks no longer route through that binary.
- **Heartbeat schema is the contract with the firmware.** Adding a field to `RenderState` only takes effect if `firmware/data.h::_applyJson` (or `_parsePrompt` for prompt fields) is updated to read it.
- **Hooks are fail-open.** When the daemon is down, hook scripts exit 0 with empty stdout and the agent falls back to its own dialog. Don't add error handling that breaks this.
- **The reducer is pure — `CheckedContinuation`s live on the engine, not in state.** Don't reach for time/random/IO inside `reduce()`.
